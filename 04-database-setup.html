The two commands — don't mix them up

  
The #1 beginner confusion in this lesson. Two commands, two completely different jobs.

  

    

      
makemigrations

      
writes the recipe — does NOT touch the database

      
    
        
  • Reads models.py and detects what changed (new model, new field, changed type…)
    • 
        
  • Generates a timestamped migration file in migrations/ describing the change
    • 
        
  • Pure Python — you can (and should) read the file it produces
    • 
        
  • Run it every time you change a model
    • 
      

    

    

      
migrate

      
cooks the dish — executes the recipes against the DB

      
    
        
  • Applies all pending migration files to the database
    • 
        
  • Also applies Django's built-in tables: admin, auth, contenttypes, sessions
    • 
        
  • Actually creates / alters tables in db.sqlite3
    • 
        
  • Records which migrations have run, so it never applies one twice
    • 
      

    

  

  
Why migrations at all? As the app grows, models change constantly. Altering tables by hand (SQL) each time would be a big hassle — migrations are Django's way of propagating model changes into the database schema automatically, with a readable, timestamped history you can even roll back.

What makemigrations actually generated. Click the highlighted parts.

  

    
from django.db import migrations, models

class Migration(migrations.Migration):

    initial = True

    dependencies = []

    operations = [
        migrations.CreateModel(
            name='Tour',
            fields=[
                ('id', models.AutoField(...)),
                ('origin_country', models.CharField(max_length=64)),
                ('destination', models.CharField(max_length=64)),
                ('number_of_nights', models.IntegerField()),
                ('price', models.IntegerField()),
            ],
        ),
    ]

Where the data lives — settings.py & engines

  
The database is configured in DATABASES inside settings.py. The model code never changes — only the engine does.

  

    
default
SQLite 3
Single-file DB (db.sqlite3 in the project root). Zero setup — perfect for development and learning. Inspect live: sqlite3 db.sqlite3 → .tables

    
swappable
PostgreSQL
Production-grade relational DB — the most common upgrade from SQLite. Same models, different ENGINE setting.

    
swappable
SQLAlchemy
Alternative engine — Django's flexibility lets you swap DB layers via settings.

    
swappable
MongoDB
Prefer NoSQL? Django can accommodate it — model code stays, settings change. This flexibility is why devs love Django.

  






  
Quick check

  
Four questions — click an answer.

  

    

      
1. You added a field to models.py. What's the correct order to get it into the database?

      

        
        
        
      

      
First makemigrations generates the recipe file from your model changes, then migrate applies it. Skipping the first step means migrate has nothing new to apply.

    

    

      
2. What does makemigrations actually do?

      

        
        
        
      

      
It only writes migration files into migrations/ — the database is untouched until you run migrate.

    

    

      
3. Where did the id column come from?

      

        
        
        
      

      
We never declared it — Django adds an auto-incremented id automatically: first record gets id=1, second id=2, and so on.

    

    

      
4. After migrate, your table in the database is named…

      

        
        
        
      

      
Django namespaces tables by app: <app>_<model>. You'll see this naming in the admin dashboard and when inspecting SQLite directly.
