The MVT Architecture

How a Django request really travels — Model, View, Template. From The Net Ninja — Complete Django Tutorial.

Follow a request through the system

Press Simulate request and watch an HTTP request travel through Django — or click any step to jump to it.

  1. 1HTTP request
    The user's browser sends an HTTP request to your Django app — viewing a page, submitting a form, etc.
  2. 2URL routing
    Django matches the URL against patterns in urls.py and forwards the request to the right view function.
  3. 3View asks the Model
    The view needs data, so it calls the Model through Django's ORM — Python objects, not raw SQL.
  4. 4Model queries the DB
    The Model translates the Python call into a database query (default database: SQLite 3).
  5. 5Records returned
    The database returns the rows, and the ORM wraps them up as Python objects.
  6. 6Back to the View
    The Model hands the Python objects back to the view. (Views can also create, update or delete records this way.)
  7. 7Context to Template
    The view passes the prepared data — the context — to an HTML template.
  8. 8Rendering (DTL)
    The template fills its placeholders {{ }} and tags {% %} with data to produce final HTML.
  9. 9HTTP response
    The view returns the rendered HTML as the response. The browser renders the page for the user.

The three components

MVT separates your application logic into three parts. Click a card to expand.

  • Represents the data structure of your application — it's essentially your database.
  • Defines the schema of your database tables.
  • Encapsulates the logic for interacting with the database.
  • With the ORM: each model class = a table, each attribute = a column.
  • You query with Python objects — no raw SQL required.
  • A Python function or class that receives an HTTP request and returns an HTTP response.
  • Processes incoming requests (view a page, submit a form, etc.).
  • Interacts with the Model to fetch / create / update / delete data.
  • Prepares data and passes it to the Template for rendering.
  • This course uses function-based views.
  • HTML files that contain the structure of your UI.
  • Include placeholders {{ variable }} and template tags {% for %} replaced with dynamic content at render time.
  • Use the Django Template Language (DTL) — very similar to Jinja 2 in Flask.

See it in code

The inventory app from the course — four small files, one full MVT round-trip.

from django.urls import path
from . import views

urlpatterns = [
    path("products/", views.products, name="products"),  # route URL → view
]
from django.db import models

class Product(models.Model):          # class  = database table
    name     = models.CharField(max_length=100)
    sku      = models.CharField(max_length=50)
    price    = models.DecimalField(max_digits=8, decimal_places=2)
    quantity = models.IntegerField()        # field  = table column
    supplier = models.CharField(max_length=100)
from django.shortcuts import render
from .models import Product

def products(request):                    # the View: request in …
    products = Product.objects.all()         # ORM query — no SQL!
    return render(request, "products.html",
               {"products": products})       # context → template … response out
<h1>Inventory</h1>
<ul>
  {% for product in products %}              <!-- template tag -->
    <li>{{ product.name }} — ${{ product.price }}</li>  <!-- placeholder -->
  {% endfor %}
</ul>

Bonus context

MVT vs MVC

MVC (classic)Django MVT
ModelModel
ViewTemplate
ControllerView

Django's "view" behaves like MVC's controller, and the template is what MVC calls the view. The framework itself (URL dispatcher + machinery) handles the rest of the controlling.

Why Django at all?

  • Rapid development — fully-fledged apps fast
  • Database flexibility — SQLite 3 default, easy to switch (e.g. PostgreSQL)
  • Built-in admin interface — site management simplified
  • Extensive ecosystem — a vast package collection
  • "Batteries included" — admin, DB, auth and more out of the box
